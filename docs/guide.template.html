Before you start

All you need is a browser. The console is started by a technical colleague on the server that holds the data, and the page you use runs on that machine — nothing is uploaded anywhere, and the page is not on the internet.

Get three things from that colleague:

  • The address, usually http://127.0.0.1:8765;
  • How to reach the server — remote desktop onto it and use its browser, or a tunnel they set up for you;
  • Which folder on the server holds the data, for example D:\quarantine\STUDY-001.

This guide is always one click away: User guide at the foot of the console's left-hand column.

One person at a time

If two people have the console open together, whoever acts second overwrites the first person's progress. Take turns, and finish a drop before handing over.

Step 1: read the drop01 · Read the drop

  1. The five steps. The current one is highlighted; each unlocks only when the one before it is done; finished steps get a ✓.
  2. The folder holding the data, as a path on the server. A folder, not a file: each file in it is one domain, named after the file (LB.csv → LB). It reads csv, xlsx, xpt, sas7bdat and parquet. Old .xls files do not work — save them as .xlsx first.
  3. Tick this for a raw EDC extract — no column names ending in DTC, dates written like 19/03/2025. Ticked: every date moves by a fixed per-subject offset and keeps the way it was written. Unticked: dates become study days. If unsure, tick it; if you forget, the next screen warns you in yellow.
  4. The study name, recorded in the contract and the manifest. Left empty, the folder name is used.
  5. The k target, 5 by default. Leave it unless you have been told otherwise.
  6. Only for a raw → SDTM training pair whose two sides spell subject numbers differently. Otherwise leave it empty.
  7. Click to start. Larger drops take longer — usually seconds, sometimes a minute.

Step 2: review every column02 · Review every column

This is the one step only you can do. The tool proposes a treatment for every column; for each one you click OK to accept it or Change to overrule it.

  1. Notes, read by colour: red means the run will stop unless you deal with it; yellow usually means a setting is wrong (such as raw left unticked); blue is information.
  2. Progress: how many columns are decided and how many are still blank. You cannot move on until none are blank.
  3. The bulk button sets every HIGH-confidence row that is still undecided to OK in one go. Read the note below before using it.
  4. Confidence: LOW, MEDIUM or HIGH. The table is sorted by it, so what the tool is least sure of comes first — that is where your attention belongs. A column also tagged QUASI-ID counts towards the re-identification measure, k.
  5. Your decision. Rows still undecided have a red background.

What to look at in a row

Each row reads left to right: Column (its name, with the domain in grey below), Proposed (what the tool intends to do, with its parameters), Why (the reasoning), and Decision (yours).

One question is enough: could anything in this column point to a particular person, and is the proposed treatment enough to stop it? Names, identifiers, dates, places and free-typed notes deserve a second look.

Overruling a proposal

  1. Click Change: the button turns brown and three boxes open beneath it. They start filled with the original proposal, so you change only the part you mean to.
  2. The new treatment, from the list. Here PKGRP goes from retain (publish unchanged) to drop (remove the column).
  3. Parameters, separated by semicolons, for example entity=subject;prefix=SUBJ. drop takes none, so this one is empty.
  4. Why you overruled it. Recorded in the contract and the manifest: when someone later asks why this column was treated this way, this sentence is the answer. Don't leave it empty.
  5. A row set to OK: the button turns green and the red background goes.
  6. Still red means still undecided.

Changed your mind? Click OK. That goes back to the original proposal and clears what you had changed.

The subject identifier row

  1. Subject numbers are replaced by random stand-ins. Two parameters usually come with this row:
    preserve_format=True — the stand-in keeps the original's length and layout: 001-0042 → 394-9212. It makes the data look like real data; it does not change how well it is protected.
    shape_prefix_from=SITEID — when a subject number starts with its site number, the stand-in starts with the site's stand-in: subject 002-0001 → 208-2262, site 002 → 208.
  2. "site segment follows SITEID" in the reasoning means the second one applies. Both are normally fine to accept.

Everything decided

  1. The bar is full and the red count has gone.
  2. Step 3, Sign it off, is unlocked. Click it.
About the bulk button

Accept the N the profiler is confident about touches only HIGH rows that are still undecided. It leaves MEDIUM and LOW alone — those you go through one by one.

It saves time, but HIGH does not mean right. At least skim every row's Why before you press it. The signature on the next screen is yours, not the tool's.

Step 3: sign it off03 · Sign it off

  1. Approved by: your own email address. Not a shared account, and not empty.
  2. An optional note, recorded with the signature.
  3. Where to save the contract, for example D:\contracts\STUDY-001.yaml. Always fill this in: otherwise the contract exists only in the console's memory and is lost when the server restarts.
  4. Click to sign. If any row is still blank it refuses and lists which.
  5. Once signed you see the signature (sha256:…) and where the contract was saved. The signature covers this exact set of rules: if anyone later edits any rule in the contract file, the run refuses it. Give the file to your technical colleague to keep.
Changing your mind after signing

You can go back to step 2 and change a decision. Doing so withdraws the signature — step 4 locks again until you sign the new rules.

Step 4: run04 · Run

  1. The output folder. A second folder with the same name plus _review is created beside it for material a person needs to see but that must not be delivered.
  2. The vault file, which records which stand-in replaced which real identifier. It is created the first time. A study always uses the same vault: a new one means a new set of stand-ins, and two drops of the same study will no longer line up — with no error at the time.
  3. Your email address, recorded in the manifest.
  4. Format: xlsx (the default) if the data will be opened in Excel — every cell is stored as text, so Excel cannot strip the leading zeros from 002; parquet for a training corpus; csv for other programs, and don't open it in Excel and save it back.
  5. Start the run. There is deliberately no box for the vault key on this page: whoever started the console has set it on the server.

Step 5: results05 · Results

  1. The run summary: rows, columns, how many rows were flagged, and the risk report. The smallest classes lines at the bottom show the attribute combinations of the people easiest to single out — don't leave this screen up while sharing or projecting.
  2. The k verdict: green met the target, red did not. k is the size of the smallest group of people who look the same on the counted columns. Check which columns were counted first: if they are only site- or country-level, even a high k says little about how hard it is to find one person. When it misses, the summary lists which columns would have to go to meet it — that is a list of costs, not a recommendation; take it to whoever owns the study.
  3. What was written. …\STUDY-001-Q3.xlsx::LB means "the sheet called LB in that workbook". manifest.json records how this drop was treated and goes with the data whenever it is delivered.
  4. Text needing a person's judgement (yellow). If this is a green Nothing flagged for adjudication instead, the output folder is the finished product and this drop is done.
  5. Shows the flagged rows on the page — as original, unredacted text.
  6. Before anything leaves the server: the manifest goes with the data, and the _review folder is deleted once you have read it.

Step 6: adjudicate flagged textonly when step 5 shows a yellow notice

Free-typed text — comments, adverse-event descriptions — can carry names, hospitals and dates. The tool picks out the suspicious rows; a person decides whether each is identifying.

Read the MARKED_TEXT column: suspect spans are wrapped in [[…]] with what the tool took them for (PERSON is a name). Ask one question per row: does this point back to the subject?

TextVerdictWhy
repeat requested by Dr. OkaforPASS keepAn investigator, not the subject

This step is not in the console yet

The console can show the queue, but recording verdicts and producing the final version still needs the command line. Ask your technical colleague, or do it yourself as follows:

  1. Open …\STUDY-001-Q3_review\review_queue.csv in Excel.
  2. Put PASS or REDACT in the verdict column. Rows already filled in were decided by policy; you can overrule them. For REDACT rows, replacement is pre-filled with only the suspect span removed, and you can edit it.
  3. Save as CSV UTF-8.
  4. On the server (your technical colleague knows how to set the key): 
    .\.venv\Scripts\deidkit.exe adjudicate "D:\tiers\STUDY-001-Q3" `
    --queue "D:\tiers\STUDY-001-Q3_review\review_queue.csv" `
    -o "D:\tiers\STUDY-001-Q3-final" --format xlsx `
    --operator you@example.com
  5. The …-final folder is the finished product.

The tool refuses to go on quite often. That is not a fault — each refusal is something it will not guess on your behalf. A red box appears at the top of the page:

Closing, refreshing, starting over

Closing the browser or refreshing the page is fine. Progress lives on the server: open the address again and the page returns to the step you left.

If you go back to step 1 after making decisions and click Read and propose again, it asks first:

  1. Keep my decisions — don't read again; go back to your review. Use this if you clicked by mistake.
  2. Discard N decision(s) and read again — throw away the decisions and read the folder afresh. Only when the data files really have changed.

Progress is lost in one case only: the console is stopped or restarted on the server. Then you start again from step 1 — a contract you saved and data already written are unaffected.

Questions

The next drop has arrived. Do I review every column again?
In the console, for now, yes. The command line can carry the signed decisions forward so that only new or changed columns need review — ask your technical colleague to use --carry-forward.
I clicked OK by mistake.
Go back to step 2 and change it any time before signing. Clicking the same button again clears it and the row turns red.
I found a mistake after signing.
Go back to step 2 and fix it. The signature is withdrawn; sign again. Anything already run under the old contract needs running again.
I don't understand a proposal. Can I just accept everything?
Technically, yes — but the signature is yours. For a column you don't understand, send its name and the text under Why to your technical colleague; that contains only a column name and a treatment, no subject data.
Can I send someone the output folder?
What can go: the data files and manifest.json (from the -final folder if there was adjudication). What must not: the _review folder, the vault file, and any intermediate files other than the contract.
Can I screenshot something to ask about it?
Screens from steps 1 to 4, yes. Not the step 5 summary or the adjudication queue — the first shows the attribute combinations of the most exposed people, the second is unredacted original text.

Not in the console yet

These still need the command line — ask your technical colleague:

  • Adjudicating flagged text (the PASS / REDACT verdicts in step 6);
  • Carrying decisions forward from a previous drop;
  • Looking up the real subject behind a stand-in, for example for a serious adverse event report — deliberately command-line only, with a reason required and logged every time;
  • More than one person at a time.

The fuller background — why the tool works this way, the cost of each treatment, what to deliver and what to destroy — is in docs/manual.html in the same repository.

Every screenshot in this guide comes from invented example data; no real subject, investigator or institution appears in it. Real data, the adjudication queue, and anything in a _review folder stay on the server.
